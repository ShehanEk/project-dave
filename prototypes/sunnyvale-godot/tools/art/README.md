# Lit-cutout art tools (C35)

Every enemy, and Dave since 2026-10-07, is a **lit cutout rig**: its parts are painted flat (no baked light), each with a matching normal map and a spec/emissive map, packed into one atlas and described by a `rig.json` that `scripts/actors/lit/cutout_rig.gd` reads. The engine's lights shade the parts smoothly through `res://assets/shaders/lit_part.gdshader`. Dave's old Rook frame sprites (his fallback) get auto normal maps so they are lit the same way.

The painters here generate placeholder art procedurally. Final art is painted by hand (or generated) and goes through the same split → normal map → atlas → `rig.json` steps. Only numpy and Pillow are needed. Every tool is deterministic: it seeds its own noise, so a rerun writes the same pixels.

## Commands

Run from the project root (`prototypes/sunnyvale-godot`):

```bash
python3 tools/art/paint_night_guard.py     # SE01 Night Guard  -> assets/characters/lit/night_guard/
python3 tools/art/paint_staffer.py         # LK01 Staffer      -> assets/characters/lit/staffer/
python3 tools/art/paint_patrol_rover.py    # M01 Patrol Rover  -> assets/characters/lit/patrol_rover/
python3 tools/art/paint_blood.py           # blood decals      -> assets/effects/blood/
python3 tools/art/make_normal_maps.py      # Dave's Rook frames -> assets/characters/rook/normals/
python3 tools/art/import_parts_sheet.py night_guard   # the pixel-art parts sheet -> assets/characters/lit/night_guard/ (pixel_art rig)
python3 tools/art/import_parts_sheet.py night_guard_smooth  # the first, smooth parts sheet -> the same folder (the old art)
python3 tools/art/import_parts_sheet.py staffer       # the pixel-art parts sheet -> assets/characters/lit/staffer/ (pixel_art rig; paint_staffer.py above rebuilds the old smooth art into the same folder)
python3 tools/art/import_parts_sheet.py patrol_rover  # the pixel-art parts sheet -> assets/characters/lit/patrol_rover/ (pixel_art rig)
python3 tools/art/import_parts_sheet.py patrol_rover_smooth  # the first, smooth parts sheet -> the same folder (the old art; rebuilds byte for byte)
python3 tools/art/import_parts_sheet.py scrapjack     # the pixel-art parts sheet -> assets/characters/lit/scrapjack/ (pixel_art rig)
python3 tools/art/import_parts_sheet.py scrapjack_smooth  # the first, smooth parts sheet -> the same folder (the old art; rebuilds byte for byte)
python3 tools/art/import_parts_sheet.py dave          # Dave's pixel-art parts sheet -> assets/characters/lit/dave/ (pixel_art rig, the hero)
python3 tools/art/import_pixel_ui.py   # the pixel UI sheets (Sheets 11, 12) -> assets/ui/pixel/ (+ x3/ for the theme)
```

Add `--preview DIR` to a rig painter to also write `DIR/<name>_preview.png`: each preview pose at 3x, then gameplay size (1x, shown enlarged), 2x, mirrored, and a flat silhouette. The previews are a software copy of the shader under a lamp, a muzzle flash and the moon rim. Write them outside the project (for example `/tmp/art-previews`).

After changing art, re-import it:

```bash
/Applications/Godot.app/Contents/MacOS/Godot --headless --path . --import
```

## Texture conventions

| Texture | Channels |
| --- | --- |
| `albedo.png` | Flat base colours with dark outlines and a mild, non-directional cavity shade; A = coverage |
| `normal.png` | Godot's 2D convention: R = +x (right), G = +y **up**, B = z stored directly (Godot decodes z = b). Flat = (128, 128, 255). Transparent texels hold the flat normal |
| `spec.png` | R = specular strength, G = gloss, B = emissive mask, A = coverage |

All three share one layout. Parts are drawn at `texture_scale` atlas pixels per world pixel (3), so a sprite is scaled by 1/3.

## `rig.json`

```json
{"name": "LK01 Staffer", "kind": "human", "texture_scale": 3,
 "albedo": "albedo.png", "normal": "normal.png", "spec": "spec.png",
 "ground_lock": true, "sole_points": [[-3.9, 4.5], [4.0, 4.5], [10.6, 4.5]],
 "parts": {"torso": {"rect": [x, y, w, h], "pivot": [px, py]}, ...},
 "joints": [{"name": "torso", "part": "torso", "parent": "pelvis", "pos": [0.3, -5.5], "z": 5, "far": false,
             "collider": {"type": "capsule", "a": [0, -2], "b": [0, -21.5], "r": 6}, "mass": 22, "limit": [-35, 75],
             "rest_dir": -90, "role": "..."}, ...],
 "sockets": {"port_light": {"joint": "head", "pos": [-2.8, -4.4]}, ...}}
```

- **Texture files** are relative to the JSON's folder. **`parts`** gives each part's atlas rect and its pivot in texels.
- **`joints`** are listed parents first. `pos` is the pivot in the parent's frame (world px, y down; the root's is in rig space, whose origin is on the floor under the character). `z` is the draw order; `far` parts are tinted darker by the rig. `limit` is the ragdoll range in degrees (null = free). `rest_dir` is the canvas angle the bone points along at zero rotation.
- **Colliders** are in the joint's local world px: `circle` {c, r} or `capsule` {a, b, r}. Every joint has a collider and a mass, so a death can turn every part into a physics body.
- **`kind`** is `human` (a ragdoll; `ground_lock` keeps the lowest of the `sole_points`, in foot-local world px, on the floor) or `machine` (posed directly by its owner; `ground_lock: false`; every joint has a `role` naming what it is, for the owner's code).
- **`sockets`** name points for lights, sparks and fluids, in a joint's local world px.
- **`pixel_art`** (optional, default false) marks a pixel-art rig; **`pixel_world`** is one art pixel in world px (1.5). See [Pixel rigs](#pixel-rigs).

## Pixel rigs

A character painted as **pixel art** (the Night Guard, the Staffer and the Patrol Rover since 2026-10-06, the Scrapjack since 2026-10-07) goes through the same importer, `import_parts_sheet.py`, with a `"pixel": {...}` block in its `SHEETS` entry. Everything is explained in the module docstring; this is the recipe.

**What the importer does to a pixel sheet.** Generated "pixel art" is not on the game's pixel grid, and its pixels are usually much finer than the 1.5 world px the backgrounds and props use (the Night Guard's came out about 2.7 times finer than the 66-pixel character the prompt asked for). So per part it (1) finds the part's own generated-pixel grid (`grid_lines`, as `import_pixel_sheet.py`), one pixel per generated pixel, colours snapped to one palette for the whole sheet; (2) bins `reduce` generated pixels into one art pixel on a grid anchored to the part's **pivot** (so every pivot is a whole art pixel), choosing the grid phase that gives the cleanest cells (it may move the pivot by under half an art pixel); (3) draws the 1-pixel near-black outline (#0B0D10) again on the new silhouette, because the generator's outline is thinner than one art pixel, and lets the neon trim and small bright accents win a cell at a small share; (4) enlarges each art pixel `upscale` times with nearest filtering into the atlas (`texture_scale` = `upscale` / `world`, so 3 / 1.5 = 2: one art pixel = 3 atlas texels = 1.5 world px); (5) makes the normal map from the art silhouette at the enlarged size and blurs it over about one art pixel, so a lamp lights smoothly across the pixel steps; (6) measures every joint offset on the parent part's own art grid and rounds it to whole art pixels. The exact neon colour(s) (`neon`, or `glow`) become the emissive mask exactly: classification happens on the generated pixels and the chosen cell colour is the table's exact entry, so nothing blends.

**Convert a character** (the Staffer and the Rover were converted this way):

1. Put the sheet under `concept-art/<id>/` and copy the `night_guard` entry in `SHEETS`: `sheet`, `rig_name`, `height` (humans) or `length` (machines), `texture_scale` 2, `neon`, and `"pixel": {"gen", "reduce", "world": 1.5, "upscale": 3, "colors", ...}`.
2. **Measure the generated pixel** (`gen`, sheet px in x and y): `import_parts_sheet.py <name> --measure` prints every part's pixel size and their average. The outline is exactly one generated pixel wide, so it is the mean width of the outline's near-black runs per axis; the measure printed 7.7 x 7.2 for the Night Guard and its entry uses 7.6 x 7.1 (its pixels are about 7% wider than tall, and 7 and 8 px wide alternately; `grid_lines` follows the cells, so the value only has to be close). Look at `gen_reduce(...)` output for a part (one pixel per cell) to check the grid is clean.
3. **Choose `reduce`** (generated pixels per art pixel). Leave it out and give `height` (humans: the soles to the crown in world px, 102 for the guard) or `length` (machines): the importer prints the reduction that makes the character exactly that size in art pixels of `world` (1.5) world px; round it and write it into the entry. The guard's is 2.7 (68 art px = 102 world px); the Staffer's, from a sheet with ~9 px generated pixels, is 1.58 (65 art px = 97 world px). A part drawn on a finer grid than the rest (the Staffer's port: ~5.7 px pixels, drawn a third of the head's width) takes its own `gen` and `reduce` in its part entry. If a part comes out too coarse to read, the choice is a finer `world` (not tried: it would no longer match the background's pixel size).
4. **Measure the anchors in sheet pixels** by viewing the sheet with a grid (a crop with a labelled line every 20 px is enough). Per part: `at` (any point inside it), `pivot` (its joint: where it rotates; an error of 5 sheet px is fine, the grid snaps it); then the guard's anchors, `neck`, `shoulder` (on the torso), `waist` (pelvis), `elbow`, `wrist`, `grip`, `knee`, `ankle`, three `soles` (heel, ball, toe), `tip` (baton). An anchor is **the next joint's pivot point on this part**: put arms' elbows and wrists a little inside the limb so the next part overlaps the one before (sleeve cuffs, boot tops). Set `emit` boxes (sheet px) on a part whose tell has no neon on it (the guard's baton tip and studs).
5. A human that is not the guard lists what differs: `joint_parts` (the Staffer: `{"near_forearm": "forearm_bare", "baton": None}`), `sockets` (`{"port_light": {"joint": "port", "part": "port", "at": (x, y)}}`, or `"pos": (x, y)` in joint-local world px instead of `part` and `at`), and, for parts the guard's rig has no joint for, `extra_joints` (the Staffer's `port` on the head and `lanyard` on the torso: `name`, `part`, `parent`, `on` = the sheet part the parent joint draws, `at` = a sheet point on it, `z`, `mass`, `limit`, `before`; the collider is fitted to the part's art unless given). `joint_z`, `joint_mass` and `colliders` override a joint's draw order, mass and collider (the Staffer keeps its old masses so its ragdoll falls as before; the sleeve roll that ends the upper arm is drawn over the bare forearm's top, so `near_forearm` is below `near_upper_arm`). Per part: `lens` (an RGB: the art pixel at the pivot corner takes that colour and glows; the port's amber light), `clip_top` (drop the sheet rows above y; the lanyard's long loop), `reduce` / `gen`. Per sheet: `skin_scale` (darkens skin-tone palette entries, 0.84 for the Staffer: a lamp overhead blew his #DFB798 face out to white; the old smooth Staffer's skin was painted darker for the same reason) and in `pixel` `edge_art` (how many art pixels the normal map rounds the rim over, 4 for the Staffer's big flat parts; default 2). Added for Dave (2026-10-07): `"neon": []` (no glow at all), `skin_tint` (`{"from", "to"}`: skin palette entries scaled per channel, a lighter skin; the test picks out skin only, not an orange jacket), `pixel.extra_colors` (fixed palette entries added to the median cut's, for small details it leaves out), a human part's own `pixel` dict (as a machine's), a part's `patch` (paint something out of the sheet: `{"box", "from"}` in sheet px, every generated pixel in the box takes the median colour of its column in `from`) and `paint` (`[((dx, dy), colour)]`: hand-placed art pixels, (dx, dy) from the pixel right of and below the pivot corner, the colour snapped to the palette). A machine keeps `place`, `wheel.places` and the sockets' anchors in chassis sheet pixels, as for a smooth machine, but no `rotate` or `scale` (a pixel part must already fit); see [Pixel machines](#pixel-machines).
6. `python3 tools/art/import_parts_sheet.py <name> --out-dir /tmp/try --preview /tmp/prev` to try without touching the game's assets (the preview is the rest pose at atlas size with the joint pivots marked). Check the printed standing height, then run without `--out-dir` and `Godot --headless --path . --import`. Tune per entry if the art is noisy: `colors` (palette size; 24 for the guard), `outline_share` (how dark a cell is made an outline, 0.26), `neon_share` (how little neon wins a cell, 0.14), `accent_contrast` / `accent_share` (small bright details), `phase` (how far the grid may move a pivot, in generated pixels; 0 keeps pivots where measured), `neon_first` (indices of glow colours that win a cell before the outline test does: a trim thinner than an art pixel, the Rover's flank strip, is otherwise eaten by its own outlines), `drop_purple` (keeps the antialiasing between a magenta glow and its outline out of the palette, so no body colour is a muddy purple), `inside_share` (how much of a cell the silhouette must cover for the cell to be art, 0.5; a tiny prop takes less so its thin parts survive), and per part `snap` and `glow_in` (see [Pixel props](#pixel-props)). A part's own `pixel` dict overrides any of these for that part (a machine's wheel: `{"phase": 0}`).
7. Update what counts the new sizes: the enemy's tuning `tell_offset` (`data/tuning/*.tres`) must be the rig's `tell` socket (the Staffer has no baton: its `grip_near` socket, and `brawler.gd` puts each hand's tell glow at that hand's `grip_*` socket); its tests (`test_lit_enemies.gd` allows half an art pixel for the soles of a pixel rig); `tests/cases/test_pixel_chars.gd` checks the flag, the pixel grid, the neon mask, the height and the joint offsets (`test_pixel_rover.gd` is the machine's, with the length, the lid and the round wheel).

**Engine** (`scripts/actors/lit/cutout_rig.gd`, only for `pixel_art: true` rigs): every part sprite uses nearest filtering (the normal and spec maps stay filtered in `lit_part.gdshader`, so lighting stays smooth); a joint is posed in rotation steps that move the farthest point it carries by one art pixel (1.5 to 5 degrees: `_rotation_steps`) so a limb changes all its pixels at once instead of edge pixels flipping one by one; the pelvis (the rig's root offset) is rounded to whole art pixels, so the soles are within half an art pixel of the floor. The rig's *world* position is not snapped: at the game's camera zoom (1.2) an art pixel is 1.8 screen pixels, so snapping would only make a slow walk stutter. A pixel ragdoll keeps the nearest filter on its parts; rotated parts show stair-steps (a corpse's limbs lie at arbitrary angles), which reads as pixel art. Wound marks are children of the part sprite and inherit its nearest filter.

### Pixel machines

The Patrol Rover (2026-10-06, `build_machine_pixel`; the smooth rover stays rebuildable as `patrol_rover_smooth` and comes out byte for byte as before) is the first machine. What it taught:

- **Size.** `--measure` gave a generated pixel of 7.9 x 7.9 sheet px for the chassis (`gen` (8.0, 7.9)); the sheet's rover is 172 generated pixels long, so `length` 92 (the old rover) would be `reduce` 2.8. The entry uses **2.86**, which makes the wheel (40 generated pixels) exactly 14 x 14 art pixels, so it is centred on its hub, and the machine 62 art px = 93 world px long (the smooth one: 92; its body box and hit zones are unchanged). The prompt's intent, about 80 art pixels long (`reduce` 2.15, 120 world px), would need a bigger body box and hit zones.
- **Anchors.** Measured on the sheet in a gridded crop and on the chassis's alpha: the arches' centres (the transparent runs at y 350 and 410: x 419 and 1112) place the wheels (and their midpoint the chassis pivot, at the arches' axle height), the top profile of the shell (flat rear deck at y 30, sloping to the nose) places the pod and the lightbar, and the sheet gave every part the size it has: the lid (354 x 151) is the rear deck panel exactly (it covers the dark open bay painted into the chassis), the battery (341 x 167) is bigger than the bay and sits over the deck under the lid (shut, it is hidden to within an art pixel; stalled, the lid swings clear and the gauge shows), the bumper overlaps the nose by one generated pixel. Every joint is one art pixel at best: the child's grid may move its pivot by up to half a pixel and the offset is rounded; check each joint in `--preview` (enlarge the preview with nearest filtering) and nudge `place` by 22 sheet px per art pixel.
- **Wheel.** A 14-pixel wheel turns badly: the generator's tyre teeth leave lumps in its silhouette and the best grid phase puts the hub half a pixel off the pivot, so it wobbled as it spun. The part entry says `"pixel": {"phase": 0}` (the grid stays on the hub) and `"symmetry": 8` (`symmetrize`: every cell takes the most common colour of its orbit under the quarter turns and the mirror), so the wheel is round at every angle and its four bolts show the spin. `cutout_rig.gd` poses it in its 5 degree steps (the largest); at a charge it turns 40 degrees a frame and the four bolts alias, as the smooth wheel's did.
- **Neon.** The flank strip is thinner than one art pixel and has an outline each side, so the cell test (`outline_share` before `neon_share`) turned it into broken dashes; `neon_first: [0]` lets the magenta win its cell before the outline test. The importer's colour for a glow is the table's exact entry (`glow` in a machine entry: `(255, 61, 213)` for #FF3DD5, the brief's `#C98A2B` amber and `#3FE0D0` teal rather than the sheet's slightly different pixels); a pixel within `GLOW_TOL` of it is that glow. Under the engine's emissive energy 1.3 an exact #FF3DD5 strip reads pink-white rather than saturated magenta.
- **Lightbar.** Its six lenses are 2.17 art pixels apart; at `reduce` 2.86 they come out as six one-pixel dots, at 2.8 as four dots and a bar. Check the lenses when changing `reduce`.
- **Motion.** The root is rounded to whole art pixels, so `patrol_rover.gd` bounces a pixel rig by one art pixel (and shakes it one art pixel in the windup): the smooth rig's 0.35 and 0.5 px offsets would round to nothing. The chassis tilt of the windup, charge and stall is posed in 1.5 degree steps; with nearest sampling an edge crawls by a third of an art pixel at each step, which reads as a rotated pixel sprite.

### Pixel props

The Scrapjack (2026-10-07, `build_prop_pixel`; the smooth gun stays rebuildable as `scrapjack_smooth` and comes out byte for byte as before). A prop has no skeleton: `scrapjack.gd` places and recoils it on Dave's aim pivot. What it taught:

- **Size.** `--measure` gave a generated pixel of 9.4 x 9.2 sheet px, so the sheet's pistol is about 123 generated pixels long (the prompt asked for 26). The smooth gun was 26 world px = 17 art px, which would be `reduce` about 7: with the importer's defaults a black slab (a 5-row part is all outline; the trigger guard, the scrap window and the second coil vanish). With the settings below and the same layout (tried in `--preview`), `reduce` 6.0 (29.7 world px, +14%, battery 6.9) loses the teal charge light (a one-row battery cannot hold a 1-pixel light) and one coil, and 5.5 (32.1 world px, +23%, battery 6.3) loses the light. Both coils and the light survive with the barrel and the battery at 5.0 and the frame and the housing at 5.5 (34.1 world px, +31%, but two pixel densities in one gun), or with everything at 5.0: **`reduce` 5.0**, the entry: 24 art px = 36 world px long (+38%), the muzzle 30 world px from the grip (22.4 before), the back of the grip 6 behind it (3.6 before). To try another, change `reduce` (and the parts' own `reduce`) and move `place` by `9.2 x reduce` sheet px per art row so the housing's bottom outline stays on the rail's top outline. The battery cell is drawn 1.35 times bigger than the look wants it; a pixel part is never scaled, so it takes a coarser `reduce` of its own (5.75).
- **Anchors** (sheet px, measured in a gridded crop and checked with `--preview`, which magnifies a pixel prop 8x). The root, the frame, pivots at the **grip** (`origin`, 235 x 346: the top of the tape, under the rail; it is the root's pivot and `place` too, so the rig's origin is the grip and `scrapjack.gd`'s `GRIP_LOCAL` still puts the fist on it). Every other part's `place` is the frame-sheet point where its pivot sits, measured on the frame's art grid (a point past the frame's front tip continues the grid at its mean cell size, `PixelPart.to_g`) and rounded to whole art pixels. The housing (pivot (900, 440), its bottom edge) is placed so its bottom outline row is the rail's top outline row: one black row between the housing and the pale rail, not two. The barrel (pivot on the bore) tucks about 4 art px under the housing and hangs two art rows lower, so its bore is 3.75 world px above the grip (the smooth gun's 2.95): a shot starts close to the aim line. The battery's top outline is hidden behind the housing. The muzzle socket is the barrel's front edge, halfway up it; the charge-light socket is the middle of the battery's teal cells.
- **Cutting a part this small.** A one-generated-pixel outline redrawn as one art pixel (5 times thicker) eats thin parts, so the entry sets `outline_share` 0.8 (an interior cell is an outline only when it is nearly all black, so the housing's scrap window stays a dark steel row and not a black slab), `inside_share` 0.35 (a cell is part of the art when the silhouette covers a third of it, so the thin trigger guard is not lost between the cells) and `phase` 2.0 (the grid may move 2 generated pixels to find clean cells). The taped grip's frayed pale marks and the rust flecks come out as a few pixels or vanish.

The generator paints the coils in a dozen oranges, and only the exact colour is the mask, so the barrel's `snap` rule makes every warm generated pixel inside the two coil boxes exactly #D9884A (`PixelPart.snap_colour`); a part's `glow_in` limits where a glow colour counts, so the rust flecks, the scrap window's orange bits and the frame never glow (`{0: [], 1: []}`: no glow at all).
- **Engine.** `cutout_rig.gd` draws it with nearest filtering as any pixel rig. The gun's turn is the aim pivot's own, continuous (no joint is posed, so `_rotation_steps` never applies): nearest sampling makes the edges crawl by a third of an art pixel as it sweeps, which reads as a rotated pixel sprite, and a sweep captured at a degree per frame shows no jerk. A rotation step would only hold the gun behind Dave's smooth arm. `scrapjack.gd` moves the arm's kick and the housing and barrel's slide in whole art pixels when the rig is `pixel_art` (the kick steps 2, 1, 0 art pixels as it settles).
- **On Dave** (since 2026-10-07 a pixel rig too, see [Dave](#dave-the-hero)) the gun is at scale 1 (hero.tscn had scaled it 0.65 for the smooth Rook), so its pixels are the world's 1.5 px; its grip is 35.5 world px from the shoulder and its muzzle 0.75 px above the aim line. ## Adding a rig

1. Copy a painter. Draw each part in its own frame: the joint pivot is at (0, 0), +x is the way the rig faces, and +y runs down the bone (limbs hang down; torso, pelvis and head point up). Paint hidden overlap under every joint, and paint far limbs and hidden sides complete.
2. Build a part from these calls:
   - `body` or `shell` for its volume;
   - `patch`, `bump`, `seam` and `ridge` for detail;
   - `tint` and `tint_stroke` for flat colour changes;
   - `emissive=1` on a patch, or `emit`, for lenses and lights.

   Never paint light, shadow, blood or glow into the albedo.
3. List the joints (parents first), write with `write_atlas` and `write_rig_json`, and check the result with `--preview`, then in the engine under a lamp with both facings.
